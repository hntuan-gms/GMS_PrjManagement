# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An MS-Project-style planner (Gantt + WBS + dependencies + resource view + Scrum/Kanban board) layered on Jira Cloud, with two-way sync. Each user logs in with their own Atlassian account via OAuth 2.0 (3LO) and picks a project they can browse — there is no shared service credential and no mock mode. `server/` is Express + TypeScript (ESM), `client/` is React 19 + Vite. UI strings and README are Vietnamese — keep new user-facing strings Vietnamese.

## Commands

```bash
# Schedule data lives in the `gms` database on the shared Cloud SQL instance
# bof-intern:asia-southeast1:intern-portal-db, alongside — but isolated from —
# the intern portal's own `intern_db` and `hnxcis`. One-time GCP wiring (database,
# user, Secret Manager entry, two IAM grants):

# Deploying is what applies it. .github/workflows/deploy.yml is the SOLE source of
# truth for the service's environment (env_vars_update_strategy: overwrite), so
# anything set on the service by hand is reverted on the next push to main.
git push origin main

# Dev — two processes; browse localhost:5173, NOT :4000
cd server && npm install && npm run dev     # tsx watch, API on :4000
cd client && npm install && npm run dev     # Vite on :5173, proxies /api to :4000

# Local dev needs its own DATABASE_URL and currently has none: this machine's IP
# is not in the instance's authorized networks, and adding it means changing
# firewall rules on an instance two other apps depend on. To bring local dev back,
# run the Cloud SQL Auth Proxy and point DATABASE_URL at localhost:5432:
#   cloud-sql-proxy bof-intern:asia-southeast1:intern-portal-db
cd server && npm run db:migrate             # optional, boot does it too
cd server && npm run db:import-overlay      # one-off: old data/overlay.v2.json -> Postgres

cd client && npm run lint                   # oxlint (the only linter; no server lint)
cd client && npm run build                  # tsc -b && vite build
cd server && npm run build                  # tsc -> server/dist

./deploy.sh                                 # build both, serve UI+API from :4000 on one process
docker compose up -d --build                # same, containerised
```

Dev goes through the Vite proxy so it is same-origin with the API and the session cookie behaves exactly as in production. Hitting `:4000` directly, or pointing `VITE_API_BASE` at another origin, breaks login — the cookie is `SameSite=Lax` and won't be sent cross-site. The symptom is "login succeeds, then bounces straight back to the login screen".

The server **exits at boot** if `ATLASSIAN_CLIENT_ID`, `ATLASSIAN_CLIENT_SECRET`, `SESSION_ENCRYPTION_KEYS`, `APP_BASE_URL` or `DATABASE_URL` is missing, or if the database is unreachable. That is deliberate: with mock mode gone there is no degraded path worth starting.

**Tests** come in two layers, and neither touches Jira or the database:

```bash
cd server && npm test && npm run typecheck:test   # node:test via tsx: computeProgress (scope, baseline), ADF/mentions, KBKT import, saved-filter validation, structure/links/JQL/import (stage 2), assistant tools
cd client && npm test && npm run typecheck:test   # card options, skills matrix, capacity, resource columns/date presets/people filter, report compare/deep link, csv, taskFilter, mentions (the comment box's @Name round trip), baseline geometry, WBS export, saved filters, stage-2 filters/undo/structure/import
```

Unit tests live in `test/` beside `src/` (outside both `tsc` build roots, hence the separate `tsconfig.test.json` typecheck) and cover only pure logic — put new pure logic in a React-free module so it can be tested (that is why `client/src/mentions.ts` is not inside `TaskDiscussion.tsx`). `e2e/mock-api.mts` answers `/api/*` from memory and runs the **real** `computeProgress`; it proves the client's behaviour, never Jira's. Each `*.e2e.mjs` is a standalone script that `run.mjs` runs in turn (the stand-in API is shared, so a file that loads a big project — `POST /api/__tasks/generate` — calls `/api/__restore` when it ends). Use a real `dblclick()` rather than `dispatchEvent("dblclick")` — the latter skipped the first click's re-render and hid a bug for a whole phase. Anything that writes to Jira (comments, mentions, priority/labels, worklogs, the AI plan's Apply) is still only verified by hand: `docs/test-reports/2026-10-15-jira-that-checklist.md`. The one earlier test pass (`docs/test-reports/2026-09-11-jira-two-way-sync.md`) predates OAuth. API calls require a session cookie, so `curl` needs a cookie jar (`-b`/`-c`) or you verify in the browser.

`client/.npmrc` sets `legacy-peer-deps=true` — `gantt-task-react` declares an old React peer range. The Dockerfile must copy it before `npm ci` or the image build fails; that's why [Dockerfile:8](Dockerfile#L8) lists it explicitly.

## Architecture

### Two data sources merged per task

A `Task` (`server/src/types.ts`) = one Jira issue + a local "overlay" record, joined in `TaskService.hydrate()`:

| Owned by Jira (read/write via REST v3) | Owned by the overlay (Postgres, `task_overlay` + `task_dependency`) |
|---|---|
| summary, issuetype, status, assignee, parent | durationDays, percentComplete, predecessors, baselineStart/Due |
| `duedate` — always derived as start + duration and pushed back on every schedule edit | |
| the site's "Start date" custom field, **discovered per site** | startDate, when the site has no such field |

Only the overlay column is unrecoverable: Jira issue links carry no FS/SS/FF/SF type and no lag, Jira has no baseline concept, and standard issues have no % field. Lose the database and dates come back from Jira while the dependency graph and baselines do not.

`hydrate()` is where the two reconcile, and the precedence matters: if Jira has a Start date value it **wins** over the overlay (and duration is recomputed from it against `duedate`); if it doesn't, an out-of-band `duedate` edit made directly in Jira shifts the overlay start to match while preserving duration. Both branches exist because of real bugs (BUG-02, BUG-03 in the test report) — don't simplify them away.

**`customfield_10059` is no longer hard-coded.** It is HHBJ-specific; on another site that ID is absent or an unrelated field, and writing a date into it would be silent corruption. `server/src/fieldDiscovery.ts` resolves it per cloudId via `GET /rest/api/3/field` and caches for an hour. When it returns `null`, writes must **omit** the field — `hydrate()`'s duedate-only branch is then the designed path, not a fallback.

Every table is keyed by the Atlassian **cloudId**, because two sites can both contain an issue called ABC-1 and `Predecessor.taskId` is a bare issue key on the wire. `store.deleteOverlay()` clears edges in both directions **within that scope only**.

Dependencies are one row per edge in `task_dependency`, not a JSON array on the successor: the cascade's hot question is "who depends on X?", which an array can only answer by scanning every task. `hasSuccessors()` is an index lookup on `(cloud_id, predecessor_key)`, and it is what lets `updateTask` skip the whole cascade — including its project-wide Jira search — for a task with no dependency edges, which is most drags.

`store` is deliberately **batch-first**: `getProjectOverlays()` loads a whole project in two queries and `setOverlays()` writes many rows in one. A per-task read was free against the old JSON file but is a round trip against Postgres, so `listTasks()` reconciles in memory and persists once — `reconcile()` is pure for exactly that reason, with the write left to its caller.

### Epics carry no assignee

`isAssignableType()` lives in **both** `server/src/types.ts` and `client/src/types.ts` and says the same thing: an Epic is a container, not work. It is enforced, not merely discouraged, because an assigned Epic corrupts every workload number downstream — an Epic's bar spans its children's full min/max (`ganttMapping.resolveRanges`), so one Epic would book its owner solid for the length of the whole phase *on top of* the children they are actually doing.

Enforced at every entrance: `createTask` and `createFromPlan` drop the field (a caller saying "an Epic for phase 2, owner Minh" means Minh leads it — failing the creation over a field we ignore helps nobody), `planner.normalize()` clears it with a reviewer warning, and `updateTask` **rejects** it with a 400. That last one costs an extra `getIssue`, but only when someone is actually being put on a task: issue type is not in the overlay, and `updateTask` is the single choke point every assignment goes through — both modals, the resource tab's drag-and-drop and the assistant's `assign_task` alike. `buildResourceLoad`/`buildWorkload` also skip Epics outright rather than trusting the rule, so data predating it can't poison the heatmap.

### Authentication

`server/src/auth/` holds the whole OAuth layer. Sessions are **stateless sealed cookies** (AES-256-GCM via `node:crypto` — no new dependencies) rather than a server-side map, because Cloud Run replaces the container on every deploy and scales to zero, so in-memory sessions would log everyone out several times a day.

**One field is the exception: the Atlassian refresh token lives in Postgres** (`oauth_refresh_token`, via `auth/refreshTokenStore.ts`), keyed by `(cloudId, accountId)` — the same identity a session cookie already carries, so the cookie never needs to name the row. It used to ride in the cookie like everything else, but it's the one field with no size ceiling: an account belonging to several Atlassian organizations gets a noticeably larger refresh token, and that pushed some real logins over the sealed cookie's ~3900-byte budget outright — `SessionTooLargeError` at `commitSession`, login failing unconditionally for that account, confirmed in production logs (`server/src/routes/auth.js:127`). Moving only this field out doesn't reopen the "in-memory map dies on redeploy" problem the stateless design exists to avoid, because Postgres is already durable across deploys here — it isn't a process-wide cache, it's the same store `task_overlay` and everything else already leans on. A rotation now writes straight to Postgres and never touches `gms_sess`, so `auth/tokens.ts`'s in-memory caches (in-flight dedupe, rotation grace, the oversized-access-token fallback) are keyed by `(cloudId, accountId)` rather than a fingerprint of the (now Postgres-resident) token value.

Three more things there are load-bearing and easy to "harden" into an outage:

- **`SameSite=Lax`, never `Strict`.** The OAuth callback is a top-level cross-site navigation from `auth.atlassian.com`; `Strict` withholds the cookie and every single login fails the state check.
- **Refresh happens eagerly in `requireAuth`, before `next()`.** Atlassian rotates refresh tokens, and `res.cookie()` after `res.json()` is a silent no-op — dropping a rotated token logs the user out on their next request with no way to diagnose it. `auth/tokens.ts` also single-flights concurrent refreshes and keeps a ~120s grace cache for the window where a second request still carries the pre-rotation cookie.
- **`requireAuth` is mounted with `apiRouter.use`**, so a route added later is protected by default. The Cloud Run service is publicly invokable — it has to be, or the callback navigation is rejected by IAM before Express runs — which makes this middleware plus `ALLOWED_SITE_HOSTS` the only access control in front of Jira.
- **Access is delegated to Jira, not to an email domain.** `ALLOWED_SITE_HOSTS` names the Atlassian site(s) whose members may log in, so a user is allowed in exactly when an admin already invited them — which is what makes guests on personal or client-company addresses work with no list to maintain. An email-domain rule cannot express that: it either excludes every guest, or admits anyone who happens to share a domain. The callback also **selects that site by hostname rather than taking `resources[0]`** — external guests routinely have their own company's Atlassian site too, `accessible-resources` has no documented order, and taking the first would drop a client guest into their own Jira.
- **`STAFF_EMAIL_DOMAIN` is not a login gate.** It decides `session.staff`, which gates `/api/ai/*` and `POST /api/progress/reports` — every route that bills against the shared Gemini key, and nothing else. The rest of `/api/progress` (live metrics, reading saved reports) stays open to guests: it costs nothing and covers only a project `requireProject` has already confirmed they can browse. The client hides the chat dock and the report page's generate button for guests rather than showing controls that always 403. `ProjectWorkspace`'s view switch applies the resource-access check to the Nguồn lực tab only — it once read `view === "gantt" || resourceAccess !== "allowed"`, written when there were two tabs, which silently sent non-admins clicking Báo cáo back to the Gantt. The email itself is **never stored** — only the derived boolean — which is what keeps `client/public/privacy.html` truthful.
- **The OAuth flow cookie is keyed per `state`, not one fixed name.** `server/src/auth/cookies.ts`'s `oauthCookieName(state)` names it `gms_oauth_<state>`. A single fixed name used to mean exactly one login could be in flight per browser: starting a second `/login` (a new tab, trying a different Atlassian account) silently overwrote the first attempt's state+PKCE verifier, so the first tab's callback came back to a cookie that no longer matched — `invalid_state`, unrecoverable, because the redirect to Atlassian had already happened. `state` is already unguessable and cookie-name-safe (base64url), so it doubles as the lookup key with no hashing; the sealed cookie *value* is still what proves authenticity, this only decides which value to read. `/callback` clears only the one cookie named after the `state` Atlassian echoed back, so a login still in progress in another tab is untouched.

`TaskService` is constructed **per request** from the session. There is no module-level singleton and no process-wide Jira identity.

### Dependency cascade

`TaskService.applyDependencyCascade()` runs after any schedule or predecessor change. It is a BFS that keeps every successor at its earliest allowed start (ASAP) — not just "no earlier than allowed": moving a predecessor earlier now pulls a successor backward too, **but only if that successor had zero slack** against the specific edge that moved (its start exactly equalled the old bound). A successor with an intentional gap keeps it; only one that was riding right behind its predecessor gets dragged along. This still isn't a full CPM backward pass — it moves what was touching a boundary, not everything that theoretically could shift — and it works by comparing against `priorState`, each touched task's position from the instant before this cascade run first touched it. Each visited node **first re-checks its own start against its own predecessors** before pushing successors — that self-check is the fix for BUG-06 (adding a new predecessor otherwise left the task itself in violation), and it doubles as the safety net for a tentative backward pull: if some other predecessor still requires a later start, this pushes the pulled successor back forward once it's dequeued. FS/SS/FF/SF each have a distinct earliest-start formula (`earliestStartFor` in `taskService.ts`, mirrored client-side in `dependencyCascade.ts` for the optimistic-drag preview); FF/SF subtract `durationDays - 1`.

Jira write failures during a cascade are collected and returned as `cascadeWarnings` rather than swallowed, except a 401 which is re-thrown — a revoked token used to leave the overlay and Jira permanently and silently divergent.

### Date handling

All dates are `YYYY-MM-DD` strings. Server arithmetic (`addDays`, `diffDaysInclusive` in `taskService.ts`) is UTC-based. The client must **not** use `toISOString()` on a local-midnight `Date` — in UTC+7 that rolls back a day (BUG-04). `GanttView.toIso()` uses local getters deliberately; `TaskEditModal` computes in UTC to match the server. Duration is inclusive: due = start + duration − 1.

### Assistant (chat)

`server/src/ai/tools.ts` is the tool registry, and the split inside it is the design. **Read tools** (`suggest_assignees`, `team_workload`, `project_progress`) are free to call and are what make the write tools worth having — the prompt tells the model to consult them before putting anyone on anything. **Write tools** (`create_task`, `assign_task`, `unassign_task`) reach Jira directly, one issue at a time, because that is what "tạo giúp tôi một task" means and staging a single issue for approval is ceremony. `create_plan` remains the path for anything bigger: a whole breakdown still lands in `ai_plan_run` for a human, because forty issues created from a misread sentence is a different kind of mistake than one. Any write sets `mutated`, which the stream reports once per turn as a `mutated` event and `ChatDock` turns into a `refreshTasks()` — nothing else in the app would know a task appeared or changed owner.

Auto-assignment (`autoAssign`, or `assign_task` with `auto: true`) ranks candidates by **fewest conflicting days first**, then by load. "Least loaded overall" is the obvious rule and the wrong one: someone at 40% for the month can still be double-booked in exactly the week the task needs, and a monthly average hides that completely. Nobody is filtered out for being busy — a fully booked team still has to do the work, and an empty list just makes the model invent something — so the conflict cost is reported instead and the model is told to say out loud why it picked someone. Tools share one `ToolContext` per turn, so a second `create_task` sees that the first already booked someone's week (`commitAssignment`).

**Everything the UI can do to a task is also a sentence** (`ai/editTools.ts`, registered alongside `tools.ts`): `update_task` (title, description, status, start/due/duration/`shiftDays`, %), `add_dependency`/`remove_dependency`, `set_baseline`, `delete_task`, `get_task`/`search_tasks`, and on a Jira Software board `move_to_sprint`, `set_estimate`, `sprint_action` (create/start/complete/update). They call the same service methods as the UI, so the cascade, the Epic rule and board scoping come for free; what the layer adds is what only a chat needs. A status is matched against the issue's *allowed transitions* by transition name, target status name, or a category word ("xong" → the one transition into a done status) — workflows name statuses differently and "To Do" isn't one on every site (BUG-05). `add_dependency` refuses a link that would close a loop (`reaches()` over predecessors): the Gantt UI can't draw one by accident, a sentence can, and the cascade BFS would chase its own tail. Irreversible actions — `delete_task`, `sprint_action complete` — return `needsConfirmation` unless called with `confirmed: true`; that check is in the tool, not only in the prompt, so an unconfirmed call can never delete. `ctx.tasks` is updated from each result (including `cascaded`), so later calls in the same turn see the moved plan. The snapshot line carries each task's predecessors, so "đã nối chưa?" needs no tool call.

Replies render through `ChatMarkdown` (bold, italics, code, links, lists, headings, simple tables) to React elements, never innerHTML — the text can quote issue titles anyone on the project wrote — and this project's issue keys in a reply become buttons that open the task. The prompt still asks for plain bold and `- ` bullets only.

**Stop reaches the server.** `routes/ai.ts` aborts an `AbortController` on `res.on("close")` when the response hadn't finished (not `req` — a request's `close` fires as soon as its body is read, long before anyone disconnects). The signal goes to Gemini (`config.abortSignal`) and is checked between passes and before each tool, so a stopped turn stops billing and stops running tools. An abort is not a failure: what streamed so far is saved, the usage is still reported, and no "chưa trả lời được" apology is appended. The client keeps the partial answer too (`commitTurn`).

**The task detail and the screen are sentences too** (all in `ai/editTools.ts` unless noted). `update_task` also takes `priority` (a spoken word — "cao", "khẩn cấp" — resolved to *this site's* priority name by `toolUtils.resolvePriority`, never sent raw) and `addLabels`/`removeLabels`, folded into the full set Jira wants from the task's current labels so the model never has to read and resend them. `search_tasks` filters by label, priority and `sprint` (a name, number, `active`, `next`, or `backlog`; one board call, then a key set — it needs `JIRA_AGILE`). `get_task_comments`/`add_comment`/`get_task_history` go through `TaskActivity` (same as the task modal), and `add_comment` resolves every name in `mentions` **before posting** (`ai/mentionText.ts`, `resolvePerson`): an ambiguous "Quang" posts nothing and comes back as a question, because a comment — and the email Jira sends — cannot be unsent. `task_digest` ("task này đang vướng gì?") is the report-page rule applied to one issue: `ai/taskDigest.ts` gathers and *measures* (overdue days, unfinished predecessors and how late each is, who waits on it, logged vs estimated hours, days without any change, last status change, recent comments) and returns plain-Vietnamese `signals`; the model only interprets them. Duplicates are code too (`ai/similarity.ts`, word overlap on diacritic-folded titles, ≥2 shared words and a 0.6 score): `find_similar_tasks` answers "đã có việc nào giống … chưa", and `create_task` runs the same check itself and returns `needsConfirmation` + `possibleDuplicates` **without creating anything** unless called with `allowDuplicate: true` — enforced in the tool like `delete_task`'s confirmation, and under a parent only that parent's children are compared ("Kiểm thử" under every Story is normal). The stopword list is short on purpose: words are compared without diacritics, so "đang"/"đăng", "bằng"/"bảng", "về"/"vé" collide and none of them is a stopword. Drafting a description is a prompt rule, not a tool: `get_task` returns the parent's title and sibling titles for context, an empty description is written straight away, an existing one is shown for approval first.

`set_view_filter` filters **what the user sees**, not Jira: `ai/viewFilter.ts` resolves words to exact ids (names → accountIds, "xong" → the statuses this site files under done, an Epic by key or title) and a `filter` SSE event carries the `ViewFilterSpec` to the browser, where `client/src/viewFilter.ts` pours it into the same `TaskFilter` (Gantt, heatmap) and `BoardFilter` (board) a person sets by hand — so it clears like one, and `ProjectWorkspace.applyChatFilter` hands the board its copy through `incomingFilter` because the board's filter is local state that restarts empty on every visit to the tab. `"me"` must never include "mình": folded it is "minh", one of the commonest given names, and "lọc việc của Minh" must filter Minh. The tool also reports how many tasks match via `countMatching`, a **mirror** of `matchesTaskFilter` (`client/test/viewFilter.test.ts` runs both over the same cases — change the rule in both places).

**Answering again and editing never delete or re-run writes.** "Tạo lại" (`regenerate`) answers the stored last question again; "Sửa" (`replaceLast`) swaps the last question and answers that. The old messages get `superseded_at` (migration 007) and every transcript/history query skips them, but `projectUsage` still counts them: those tokens were spent. A turn that wrote to Jira (a `mutated` event — created task, comment, logged time…) is stored with `mutated = true`, and `prepareRetry` refuses both with a 409 *before the stream starts*: answering it again would write it again. The client hides the buttons for the same reason and puts the old answer back if the server refuses.

**Files attached to a message are read, not kept** (`ai/attachments.ts`, migration 008). Images (PNG/JPEG/WebP/GIF), PDF and plain text/markdown/CSV/JSON, at most 4 files, 5 MB each, 12 MB together, validated on the decoded size; text is decoded into the prompt, the rest goes to Gemini as `inlineData` for that one turn. Only name, type and size are stored, so a later turn is told "[Đính kèm: x.png] (nội dung tệp không còn trong lịch sử)" and a turn that had files cannot be regenerated or edited — the file it was answered from is gone. `POST /api/ai/chat` has its own 20 MB body parser mounted **after** `requireProject`: the global `express.json()` skips that one route, so nobody unauthenticated can make a public Cloud Run service read megabytes. Note `client/public/privacy.html` says nothing about the assistant at all (chat text and project data already go to Google's Gemini, and now user files do too) — that needs a decision from whoever owns the privacy statement.

**A turn always ends in words.** `streamChat` runs up to `MAX_TOOL_PASSES` (5) tool rounds and executes every call the model makes; when the budget is spent — or a pass produced only thoughts — one last pass runs with `functionCallingConfig.mode = NONE`, so the model can only answer. The old bound was two passes, and a plain "đổi GPM-104 cho Quang" needs three (find the person, assign, reply): the second pass's `assign_task` was never executed and the turn ended on thought summaries, which users read as the assistant thinking aloud forever — and since empty-content turns are dropped from `recentTurns`, every "tiếp" replayed the same unfinished request. The team roster (name — accountId) is in the system prompt for the same reason, and `assign_task`/`create_task` take `assignee` as a spoken name resolved server-side by `resolvePerson` (diacritics-insensitive, all typed words must match; several matches come back as a question, never a guess).

**Conversations are private to the account that started them.** Every read and write of `ai_chat_session` goes through `chatStore.ownsSession` (cloudId, projectKey, **created_by**). `created_by` used to be recorded but not checked, and the browser kept one session id per machine (`gms.chat.sessionId`), so a second person logging in on the same computer continued the first person's chat. `ChatDock` now keys the remembered id by site + account + project and clears the legacy key; the switcher lists only the caller's sessions (titled from the first question, renameable). Deleting is soft (`deleted_at`): the messages' token counters are the project's spend ledger, and "Cả dự án" usage must not drop because someone tidied their chat list.

`ChatDock` docks bottom-right, collapsed to a pill. Planning is a **tool the assistant calls**, not a separate mode: "chia việc giúp tôi" and "dự án trễ mấy task?" are the same kind of request from the user's side, and making them pick a mode first pushes the classification onto them.

`POST /api/ai/chat` streams **SSE** (`fetch` + manual parsing client-side, since `EventSource` can only GET and the message belongs in a body). `X-Accel-Buffering: no` is required or Cloud Run buffers the whole response and delivers it in one lump. Errors after the first byte go down the stream as an `error` event — the 200 is already sent.

Reasoning streams separately from the answer (`thinkingConfig.includeThoughts`, parts flagged `thought`) and renders above it, collapsed. The first token of a real answer can be ten seconds away when the model is thinking or building a plan, and a blank panel for that long reads as a hang.

Project state is injected into the system prompt rather than fetched by a tool — cheaper than a round trip at this size, and simple questions answer in one call. The snapshot is capped and drops `done` tasks first.

Token usage is stored **per message**, with Gemini's four counters kept in separate columns (`prompt`/`output`/`thought`/`cached`). They price differently, so a single total can't be turned back into money, and a session's cost is only attributable if each turn is stored on its own.

**Cost in money comes from configuration, never code** (`ai/pricing.ts`): `GEMINI_PRICING="model=input/output[/cached];…"` in currency per 1M tokens, plus `GEMINI_PRICING_CURRENCY`, both repo variables in the deploy workflow (`overwrite` strategy again). Semicolons, not JSON — the deploy action splits `env_vars` on commas. `sessionUsage`/`projectUsage` group by model and price each group at its own rate (a session can span a `GEMINI_MODEL` change); Gemini's prompt count *includes* the cached part, thinking tokens bill as output. A model with no entry contributes no cost and the total is marked `partial`; with no entry for any, `cost` is `null` and the panel says why instead of showing 0.

### Assignment without a skills matrix

`resource_profile` is the declared answer to "who does what", and until someone opens the Nguồn lực tab and fills it in it is empty. `ai/roleEvidence.ts` derives evidence from the project's own Jira history instead — which issues each person was assigned, and the words in those summaries. It reports evidence ("12 issues, words: api, endpoint"), never a conclusion ("Backend Developer"): a keyword count is weak, and a job title would hide how weak. The prompt tells the model to leave `assigneeAccountId` **empty** when nothing clearly fits — an unassigned task a human fills in beats a confident wrong assignment.

### Resource view

**Who counts as a team member is its own problem** (`server/src/projectMembers.ts`). `/user/assignable/search?project=KEY` looks project-scoped but answers "who holds the *Assignable User* permission", which on a company-managed site is granted site-wide — a five-person project lists everyone with a licence, capped at 100 with no paging. Jira's declared answer is the project's **roles** (what an admin edits under Project settings → People), so that is tried first: `GET /project/{key}/role`, then each role's actors, expanding group actors via `/group/member` (roles are usually granted to a group, so without that expansion a role read returns a group name and no humans). The role URLs Jira returns are absolute **site** URLs, not gateway ones — only the trailing role id is usable.

The fallback is **not optional**: reading project roles requires *Administer Projects* on that project, and every user here logs in as themselves, so a 403 is the ordinary case for a developer, not an error. It degrades to assignable users and reports which one you got in `memberSource`, because "why is this stranger in my team list" has no answer on screen otherwise. Cached 5 minutes per (cloudId, projectKey) — resolving it costs one call per role plus one per group.

`resource_profile` and `resource_absence` (both via `server/src/resourceStore.ts`, exposed as `/api/resources`) hold the only two things Jira has no field for: how many hours a day a person actually has, and when they are away. Everything else about a person — name, avatar, account id — comes from Jira on each load, so the tab is never a second, staling copy of Jira's directory. A person with no row gets `DEFAULT_CAPACITY_HOURS`, which makes an empty table a valid state rather than a setup step.

**The load itself is computed on the client** (`client/src/resourceAllocation.ts`), from tasks `ProjectWorkspace` already holds. That is the whole reason it lives there: the heatmap has to recolour while a Gantt bar is still under the cursor, and a round trip per drag would reintroduce exactly the lag the cascade work removed. `buildResourceLoad()` produces one `DayLoad` per person per day, and the heatmap, the per-person grid and the toolbar badge are all views over that same array — a colour and a number can't disagree.

Demand per day is `estimateHours / working days in the task's span`, falling back to a full working day when Jira has no `timeoriginalestimate` (most tasks). The fallback is what stops the sub-50% band from being dead code on a team that doesn't estimate. The rate is derived from the task's **whole** span, not the visible window, or scrolling the heatmap would change how loaded someone looks. Weekends and absence days have zero capacity; work landing on one is its own band (`off-violation`), louder than "busy", because nobody is going to do it.

Two deliberate departures from a naive reading of "show who's overloaded":
- **Four non-overlapping bands**, split at 50%: "green under 100%, yellow under 50%" overlap, and a 30% day would be both. Yellow means "has room for more work", which is a different message from green.
- **`percentComplete` does not scale demand.** It's an overlay field most teams never fill in, and halving someone's load off a number nobody maintains hides real overload. Tasks Jira calls *done* drop out entirely — a finished task is not a claim on anyone's time.

`findOverlaps()` survives alongside the hours model because it answers a different question: two half-day tasks on the same day are not an overload, but they are still two things at once, and the detail grid marks them.

`server/src/workload.ts` is the server's **mirror** of the same model, the arrangement `earliestStartFor`/`dependencyCascade.ts` already uses. The client copy owns everything about *presenting* load (colour bands, week aggregation, overlap pairs); the server copy owns only the numbers needed to answer "who should take this?", so the duplicated surface is three rules — zero capacity on weekends and absences, hours spread across a task's own working days, no estimate means one full day — and nothing else. Change those three in both files.

**The tab is two rows of chrome and then the table** (`e2e/resource-layout.e2e.mjs` is the contract). Row 1 is the shared `FilterBar` with the tab's own controls in its slots — `leading`: the Mức tải/Kỹ năng switch, the member search, saved filters; `trailing`: the period arrows, Từ/Đến, one "Khoảng: …" menu that holds the six presets (`resourceColumns.RANGE_PRESETS`; its label is read back from the window by `currentPreset`, "Theo dự án" being `range === null`), the column scale and CSV. The window is moved by a **slider** (`ResourceScrubber`, `resourceTimeline.scrubExtent/slideWindow/resizeWindow`): the track is the whole project plus a margin, the thumb is the window on screen — drag it to slide, drag an end to widen/narrow, click the track to jump, arrows move a week. It replaces the Từ/Đến inputs, which live on in the "Khoảng" menu for exact dates; the track only ever grows (`reach`), or it would rescale under the pointer mid-drag. Its width is fixed (`--rv-scrub-w`, narrower under 1400px) and nothing in the right-hand group may shrink — a squeezed "Cột" select wraps and makes the bar taller. It must stay one row at 1280px — the member search is the thing that gives way (`.tf-search.rv-member-search` needs the doubled class to beat `.tf-search`'s later `max-width`). Row 2 is the KPI pills, which **are** the people filter (`Tất cả / Có việc / Đang quá tải` over `peopleCounts`/`filterPeople`; the old "chỉ hiện người đang có việc" checkbox is gone, so `buildResourceLoad` is always called with `includeIdle: true` and "Hiệu suất TB" averages everyone), the unassigned toggle and a four-item legend (the red "work on a day off" hatch is explained in the "Ngày nghỉ" tooltip, not a fifth swatch). Where the member list came from is an ⓘ (`InfoTip`, `position: fixed` — an absolutely placed panel is clipped by the heatmap's scroll container) beside the THÀNH VIÊN header, tinted as a warning in the assignable-users fallback.

**The columns fill the table.** `.rv-grid` is `width: 100%; min-width: min-content`, a cell is `flex: 1 0 var(--rv-cell)` and a month band `flex: <span> 0 …`, so a few columns stretch to the edge and many keep their minimum width and scroll. Everything positioned over the columns is therefore a **share of the track, not pixels** (task bars, day-off bands, the today mark; the track's rules are a `background-size: 100% / --cols`). The month band has three label lengths (`monthLabel`: "Thg 10/2026" / "T10/26" / "T10") switched by a container query on the band's own width, so a month with four days showing cannot run into its neighbour; cell tooltips are `cellTooltip` (DD/MM/YYYY, "Ngày nghỉ" instead of "0h / 0h").

**The resource tab must not wait on Jira to appear.** The tab is hidden until the pool fetch answers (the server decides access through the member lookup, the slowest call on the page), which on every F5 made "Nguồn lực" pop in last and shove "Báo cáo" aside. The last *allowed* pool is now kept in `viewCache` (`resourcePool`) and used as the starting state; a refusal drops it, and the server still enforces access, so the worst case is the tab showing for a moment to someone whose access was just withdrawn.

**A person opens inside the table.** Clicking a row expands `ResourcePersonBlock`'s tasks directly under it, on the heatmap's own columns: `resourceColumns.columnSpans` gives the day/week/month columns (same breaks as `aggregateWeeks/Months`) and `placeBar` positions a task to the day inside a week or month column as a fractional column count, drawn with `calc(var(--rv-cell) * n)`. The overlap warning is a compact banner right above the rows and the two colliding rows are tinted. The block (row + opened tasks) is the drop target, so a task dropped anywhere on a person is given to them. What is *edited* about a person — role, hours/day, leave, skills, note — is `ResourceProfileDrawer`, a slide-over opened from the row's pencil or the opened block's "Hồ sơ & Kỳ nghỉ"; one "Lưu thay đổi" writes only what changed (profile PUT and/or the leave typed in the form; stored leave chips still edit/delete immediately) and Esc asks before discarding.

**Work nobody owns is a floating card, closed by default** (`ResourceUnassigned`, opened by the warning pill). It is non-modal, draggable by its header, filterable, and goes translucent *and* stops catching the pointer while a task is dragged or the card is moved (set a tick after `dragstart` — restyling in the handler itself would fade the browser's drag image), so the rows beneath it can be seen and hit. Because a card that both covers rows and accepts drops would turn a drop meant for a person into an unassign, **taking a task off someone is a separate strip at the bottom of the window** (`.rv-un-strip`), mounted only while an assigned task is being dragged, whether or not the card is open. `--z-float` (40) sits under popovers so a filter menu opened over the card is not hidden.

**Assignment is drag-and-drop**: drop a task on a person's block to give it to them, on the strip to take it back; "Chuyển…" on an opened task row and "Gán…" in the card are the keyboard/touch paths. The drag payload is held in React state rather than read back from the `DataTransfer` — `getData` is write-only during `dragover` in Chrome and Safari, and the targets need to know what is coming to decide whether to light up at all. `handleAssign` in `ProjectWorkspace` is optimistic through the same `seq`/`taskVersion` guard as every other mutation, because the heatmap recolours from `tasks` and waiting for Jira would leave the cell the user just dropped onto showing its old load.

### Board & sprints (Bảng tab)

**The board is Jira's, not ours.** `server/src/agile/boardService.ts` reads a Jira Software board on every load (columns and WIP limits from its configuration, rank order, active/future sprints, the board's own estimation field) and writes back the moves a board exists for: transition, rank, move to sprint/backlog, sprint create/start/complete, estimate. There is no board table to drift. The one thing layered on is `blockedBy`: unfinished predecessors from `task_dependency`, which Jira issue links can't express — a card blocked by work that isn't done is marked on the board, in the backlog and in the AI prompts.

**The Agile API needs granular scopes, behind `JIRA_AGILE`.** Jira Software "doesn't support classic scopes": `/rest/agile/1.0` answers 401 "scope does not match" to a `read:jira-work` token. `AGILE_SCOPES` in `auth/config.ts` is exactly what the called endpoints declare in Atlassian's OpenAPI spec. They are requested only when `JIRA_AGILE=on`, because a scope the Atlassian app lacks fails `/authorize` for everyone — so the order is: enable them on both apps in the developer console, then set the repo variable. Until then, and for a session whose token predates the switch (the gateway's scope refusal is caught), `snapshot()` falls back to a **status board**: columns from the project's statuses over the platform API, no sprints or rank, with `fallback.message` saying what is missing. `requestedScopes()` is a function rather than a constant so it reads the env after dotenv.

Writes are scoped to the session's project: keys must carry its prefix and a sprint's `originBoardId` must be one of the project's boards. A drop resolves the target column to the first of its statuses the issue's workflow can reach (`moveCard`); the client asks `GET /board/issues/:key/transitions` on drag start and lights up only reachable columns, instead of failing after the drop. Rank uses before/after neighbours in the visible list, chunked at Jira's 50. Completing a sprint moves unfinished work to the target the user chose *before* closing, rather than trusting what the close call does with open issues. Dropping a card into another person's swimlane also assigns it — through `updateTask`, so the Epic rule still applies.

**Sprints exist only on Scrum boards** — a project whose only board is Kanban has none, and the tab says so with a "Tạo board Scrum" action rather than leaving the user to wonder where Sprint went. `createBoard` is two calls because a Jira board is always a view over a saved filter: `POST /rest/api/2/filter` (`project = KEY ORDER BY Rank ASC`; the platform filter API has no v3 path and needs only the classic `write:jira-work`), then `POST /rest/agile/1.0/board` located on the project. `ORDER BY Rank` is load-bearing — a board over an unranked filter can never be reordered. The project's existing boards are untouched, and the 5-minute board-list cache is dropped so the new board appears at once.

`BoardView` is optimistic like the rest of the workspace, with its own staleness guard: a snapshot fetched while a move was in flight is discarded, and the board re-reads once the last move settles (which is also what corrects a move Jira refused). Status/assignee changes call `refreshTasks()` so the Gantt and report follow.

**The Bảng tab is dense on purpose** (`e2e/board-kanban.e2e.mjs` is the contract; mock API has a Scrum and a Kanban board):
- **`view` is derived, not stored.** `scrumView` is what the Scrum segmented control last chose; `view = scrum ? scrumView : "board"`. Switching from a Scrum board's Backlog to a Kanban board used to leave the state on `"backlog"` — neither render branch matched and the tab was blank until F5. Don't render off the raw state.
- **One control for boards**: `.bd-switcher` (a `Popover` menu) lists the project's boards with a kind badge and holds "Tạo board mới…"; it replaced the `<select>` and the "+ Bảng" button. There is **no refresh button of its own** — the header's "Đồng bộ từ Jira" does `setTasks`, and the board re-reads whenever `tasks` changes. The "Kanban nên không có Sprint" explanation is a ⓘ popover beside the kind badge (`kanbanOnly`), not a banner; the `fallback` and `truncated` banners remain.
- **Filters**: the value pickers sit behind one "Bộ lọc" panel (`FacetAccordion`, shared with the Gantt's `FilterBar` — same markup, so `toolbar.mjs` helpers keep working) and active ones are chips on a second line inside `.bd-filters`. **"Trạng thái" is not offered on the board** (its columns are statuses); it comes back on the Backlog and while a status filter is on (the assistant can set one).
- **Empty columns fold** into a 40px strip (`KanbanBoard`, `folded` set in `localStorage`, per board). A column only *shows* folded while it is empty, so a dropped or arriving card is never hidden; dropping on a strip unfolds it. The grid is `--bd-template`/`--bd-minw` set inline, not `repeat(n, …)`.
- **"+ Tạo việc" exists in every column** (not unmapped ones) and shows on hover/focus (always on touch). Created from a column other than the first, the issue is made, then `moveCard`ed to that column's statuses; a workflow that refuses the move is a notice ("đã tạo … nhưng không chuyển được"), not a failed creation.
- **Cards** are ~25% shorter: summary clamps to 2 lines, the Epic pill and the warnings (blocked / flag / idle days) share one `.bd-card-meta` line (Epic truncates first), type is `IssueTypeIcon` (mapped through `canonicalIssueType`, so "Lỗi" gets the Bug glyph) and priority is `PriorityMark` (chevron up / equals / chevron down, real Jira name in the title). The Backlog rows use the same two components.

**Sprint numbers are computed, the AI reasons** (`agile/sprintMetrics.ts`, `ai/sprintAi.ts`, routes under `/api/ai/board`, staff-only). Days are *working* days in the browser's timezone (`tzOffsetMinutes` from the client — a sprint starting 17:00Z is a different calendar day in Vietnam). Velocity is estimate completed inside each closed sprint's own window, from issues whose `closedSprints` include it; Jira's chart also knows *committed*, but that comes from the sprint report, which has no public API. The burndown replays resolution dates against current scope — scope added mid-sprint looks like it was there from day one, since the board API has no changelog.
- **planSprint**: code derives the budget (mean of the last 3 sprints' velocity) and each person's availability from `resource_profile`/`resource_absence`; the model picks from the rank-ordered backlog with a goal and reasons, and says what it deliberately left out. Picks are re-sorted to rank order and re-totalled here, and code adds the warnings (over budget, unestimated, depends on work in no sprint, someone away all sprint). Nothing moves until the reviewer applies it.
- **estimateIssues**: reference-class estimation against this board's own finished, estimated work (spread across values, `estimationReferences`), snapped to the Fibonacci scale; suggestions render as ghost chips accepted one by one.
- **sprintInsight**: the stand-up brief over computed pace (done% vs elapsed%, ±10 points), blocked, flagged and stale (in progress, untouched ≥3 working days) work; forecast, today's actions with owners, and descope candidates that move to the backlog in one click.
The chat's `sprint_status` tool returns the same computed facts.

### Status, duration, estimate, attachments

**Statuses come from the issue's workflow, never a list in the client.** The edit modal used to offer a fixed Backlog/To Do/In Progress/Done, and `transitionIssue` matched the transition *name* exactly — BUG-05: on a site whose status is "In-Progress" (or "Pending") the move failed with an English error while Jira's own UI did it fine, and "Pending" was never offered at all. Now the modal lists `GET /tasks/:id/transitions` (target status names) and sends the transition **id**; `transitionIssue` still accepts a name and compares with `foldName` (case, spaces, hyphens, diacritics removed) against the target status first, then the transition label. A refused move is a `JiraTransitionError` → 400 with the allowed targets, not a 500. On the board, a status no column maps — Jira hides it too, under "Unmapped statuses" — gets a trailing `unmapped` column when issues sit in it, so those cards don't silently vanish.

**A status change can need more than a click** (`server/src/transitionFields.ts`, `TaskService.applyTransition`). Jira refused a move to Done with a bare 400 — "Vui lòng nhập RootCause" — and the UI had no way to fill the box. Two sources, one answer: a field on the transition's own screen is read up front (`GET /tasks/:id/transitions` returns `fields` for each, via `expand=transitions.fields`); one only a workflow *validator* checks is named in the refusal, so it is looked up among the issue's `editmeta` fields (by id when Jira keys the error, else by name with case/spacing/diacritics folded — "RootCause" ↔ "Root Cause"). Either way the API answers 400 `TRANSITION_FIELDS_REQUIRED` with `details.fields` (id, name, kind, options), and the caller sends the values back as `transitionFields` (field id → what was typed; an option's id for a select; ADF is built server-side for textareas). The refusal is matched against the transition's own screen as well as `editmeta` (a box that exists only on the move's screen — not required there, demanded by a validator — is in neither the required list nor the edit fields; that was the "Mở công việc trên Jira để xem điều kiện còn thiếu" dead end for RootCause on the way to Resolved), and when the sentence names no field we can find, the screen's other fillable boxes are offered with `optional: true` ("có thể là ô này", not insisted on) rather than a dead end; the server logs a `[transition]` line with the screen's field names for that case. Kinds Jira allows but a one-line form cannot fill (users, multi-selects) are `unsupported` and point at Jira instead of guessing; any other refusal is `TRANSITION_REFUSED` with Jira's sentence, not a 502. `AppError` carries `details`, `ApiError.details` reads it. The detail window shows the boxes under the status select; the bulk bar's `BulkStatusMenu` asks each *kind of issue in one status* what its workflow allows (offering every status the project has promised moves that then failed one by one), lists only reachable targets with "n/m", and a refusal naming fields in the middle of a bulk run opens one dialog and sends the rest again. Pure rules (`neededFieldsFrom`, `missingFields`) are in `client/src/transitionFields.ts`.

**Duration is whole calendar days; effort is the estimate.** `due = start + duration − 1` has no meaning for 1.5, so the server `ceil`s every duration. The forms accept a fraction anyway and say what happens (`DurationHint`): the bar takes the next whole day and, if no estimate was typed, the Original estimate is filled with days × 8h — which is what the resource heatmap reads. Number fields use `NumberInput`, which keeps a text draft and commits only parseable, in-range values: the old `Math.max(1, Number(v))` on every keystroke snapped an emptied box back to 1 with the caret after it, so typing "1.5" produced "11.5". It also accepts a comma decimal.

**Original estimate is written through `timetracking`** (`setOriginalEstimate`), on its own call and *before* the rest of an update, so a project whose screens lack Time tracking fails with a message about the estimate and changes nothing else. On create it never fails the creation (the issue already exists — failing would invite duplicate retries); it comes back as a bulk-create `warning`.

**Attachments go up one file per request as the raw body** (`express.raw`, name in `X-File-Name`), re-wrapped by `jiraClient.addAttachment` into the multipart form Jira wants, with `X-Atlassian-Token: no-check` (without it Jira rejects the upload as XSRF). That avoids a multipart parser dependency, and one rejected file doesn't lose the rest. Links are Jira *web links* (`/remotelink`), not text in the description. Both need only `write:jira-work`. A create form holds them as `PendingAttachments` until the issue keys exist, then attaches the same set to every task in the batch; pasting a screenshot anywhere in either modal adds it. Attachment *content* is proxied only for the detail window's preview/download (`GET /tasks/:id/attachments/:attId/content`, fetched as a Blob by `api.getAttachmentBlob` so the call carries the tab's project): the id must be one of *this issue's* attachments, only raster images (`png/jpeg/gif/webp`, `?inline=1`) are ever served inline — everything else, SVG included, is `Content-Disposition: attachment` with `nosniff` and a sandbox CSP, because it would otherwise run on our origin — and a file over 30 MB says to open it in Jira. `DELETE /tasks/:id/attachments/:attId` removes one (same ownership check), after an in-app confirm.

**The WBS table's columns are chosen per browser** (`gms.gantt.columns`): type, status, priority, assignee, start, due, duration, estimate, spent, %. Dates and duration read the bar's resolved range, so an Epic's columns roll up its children like its bar does. `spentHours` and `priority` ride on the existing task search.

**Labels and priority ride on the same search and the same PATCH.** `labels` is in `SEARCH_FIELDS` and on `Task`; `updateTask` writes `fields.labels` (the *full* set, replaced not merged, whitespace folded to `-` because Jira labels cannot contain spaces) and `fields.priority = { name }`. `GET /priorities`, `/labels` and `/issue-types` feed the pickers; `CreateTaskModal` reads the project's real issue types from the last one, falling back to the old fixed list while it loads or if it fails.

### Task detail: comments and history

`server/src/taskActivity.ts` is the comments and changelog of one issue, Jira's own and with no table of ours (the usual reason: a copy would disagree with the one people read in Jira). Routes sit under `/api/tasks/:id/comments` and `/activity`, and refuse a key that is not exactly `<PROJECT>-<digits>` (`ownKey` → `TaskService.assertOwnKey`; a bare prefix test would let `PRJ-1/../x` through into a Jira URL). A mention travels as `@[Name](accountId)` in the text this API speaks: `adf.commentToAdf` turns it into a real ADF `mention` node, which is what makes **Jira** notify the person — no notification code exists here and none should be added. `adfToCommentText` flattens whatever was written in Jira's own editor (lists, quotes) to lines rather than dropping it. Only the author can edit or delete a comment (`mine`; Jira enforces it again). The changelog is paged (capped at five pages) and drops Rank/worklog noise; the client (`TaskDiscussion.tsx`) translates the common field names.

### Filters, bulk actions and CSV

**One filter over `Task[]`** (`client/src/taskFilter.ts`) is shared by the Gantt and the resource heatmap and held in `ProjectWorkspace`, remembered per site + project in localStorage (the free-text box is deliberately not restored). Same facet semantics as the board's `BoardFilter` — empty set means no restriction, `"none"` is unassigned, "Của tôi" is the signed-in account id inside `people`. The Gantt keeps a match's ancestors (`searchKeep`) so indentation stays meaningful. The resource tab ignores the `people` and `text` facets (it has its own member search, and a person picked on the Gantt would blank everyone else) and says out loud when a filter is narrowing the load it draws. The board keeps its own `BoardFilter` over `BoardIssue`, extended with status/Epic/priority.

**Saved filters** (`saved_filter`, migration 010; `server/src/savedFilters.ts` validates, `savedFilterStore.ts`, `routes/filters.ts`; `SavedFilterMenu` passed as `FilterBar`'s `leading` slot — after the search box on the Gantt, first on the resource tab) give that same filter a name on the server. Visibility is two-valued — private, or `shared` with everyone who can open the project — and only the creator can change or delete one: update/delete are `WHERE created_by = $me`, so someone else's filter is a 404, not a 403. The spec is the facets without `text` (the search box is never a saved view, for the localStorage reason above), and the saver's own account id is stored as `"@me"` (`client/src/savedFilters.ts`), so a shared "Của tôi" shows each person their own work rather than the creator's. Applying one replaces the whole shared filter, people included, even from the resource tab. Only account ids are stored; creators' names come from `listUsers()` on each GET. The board has no saved filters.

**Bulk edits on the Gantt selection bar run sequentially** (`runBulk`): each is a Jira write plus possibly a cascade, so a burst would rate-limit and interleave. Failures are collected per task, Epics are skipped for assignment up front, and an Epic with children is skipped for date shifts (its bar is its children's span). The same bar's "Baseline…" freezes the current schedule as the baseline (or clears it) — the write the assistant's `set_baseline` makes — because issues synced from Jira start with none and nothing else in the UI sets one. It asks before overwriting an existing baseline, and skips an Epic with children (its baseline is drawn as its children's span).

**CSV export** (`client/src/csv.ts`) is UTF-8 with a BOM — without it Excel opens Vietnamese as mojibake — and prefixes a `'` to any string cell starting with `= + - @`, because issue titles are typed by anyone on the project and an exported sheet must not run what a teammate wrote. The WBS export always appends the overlay data Jira's own export lacks (`client/src/wbsExport.ts`): % (unless already a visible column), predecessors as `KEY TYPE±lag`, the resolved baseline and the slip in days — a number, so a negative one isn't neutralised into text.

### Task structure, links, JQL, release lines, undo, import (phase 2 · stage 2)

**Components, fix versions and sprint ride on the task.** `components`/`fixVersions` are in `SEARCH_FIELDS`; `sprint` is read from the site's Sprint custom field, discovered per site (`fieldDiscovery.getSprintFieldId`, sharing one cached `GET /field` with the Start date lookup) and readable with the ordinary `read:jira-work` scope — it does **not** need `JIRA_AGILE` (`pickSprint`: running, else next, else latest closed). Components and versions are not free-form in Jira: the edit modal only *picks* from `/components` and `/versions` (`NamePicker`), and the chat's `update_task` matches a spoken name to the project's own spelling before writing (`mergeNamed`).

**Moving a task in the WBS is checked before Jira is asked** (`server/src/structure.ts`, mirrored for the pickers in `client/src/structure.ts` — change both): no loop (a parent may not be the task or anything beneath it), a Sub-task cannot be a parent, an Epic has no parent, a Sub-task needs one, and a task with an owner cannot become an Epic (the Epic rule seen from the other side). `updateTask` does it first of all, with one project-wide read of parent+type. Jira may still refuse a type change whose workflows differ; that message is shown as is.

**Issue links are information, never scheduling.** They live in `taskExtras.ts` and are shown beside — not among — the FS/SS/FF/SF dependencies: a Jira "blocks" has no type or lag in our sense and moves no bar, and the modal says so. The routes are `/tasks/:id/issue-links` because `POST /tasks/:id/links` is already the web-link (remotelink) upload. For "A blocks B" Jira's `outwardIssue` is A and `inwardIssue` is B; `addLink` maps the viewed issue's side to that, and a delete only goes through for a link that belongs to the issue. Watchers are only ever the signed-in user, and listing them needs a Jira permission most people lack (`listed: false` says so).

**One filter, three extra ways to set it.** `TaskFilter` gained `components`, `versions`, `sprints` and `jql` (beside `priorities`). *Saved filters* are the section above's — the same `saved_filter` table and menu — and a saved spec carries these four too (`validateSpec` accepts them; a filter saved before they existed opens with them empty, and a JQL alone is something worth saving). *JQL* is not parsed by us: the string goes to Jira as `project = KEY AND (…)` with a trailing ORDER BY cut (`scopeJql`), runs with the user's token, and the keys come back cut to this project's (a clever closing parenthesis cannot widen the scope into someone else's data). Its answer reaches the filter as `FilterContext.jqlKeys`; until it arrives, **or if the JQL is wrong**, it restricts nothing — a typo must not blank the chart — and the error is shown beside the box. `ProjectWorkspace` keeps the keys matched to the text through one effect on `taskFilter.jql`, so typing one, applying a saved filter, "Xoá lọc" and a reload all behave alike.

**What is drawn besides bars** (`TimelineMarkers`, over `useBarRects` — the same DOM measuring `DependencyOverlay` uses, now shared): a diamond on milestones and a vertical line at each release date. Baselines are `BaselineOverlay`'s (Gantt rendering section below); an earlier second implementation was dropped when the two branches met. Positions come from `timelineGeometry.ts` and are measured from the nearest bar's *own* pixels-per-day, not one global scale: in Month mode a column is 28–31 days but always the same width, so a global scale would drift. Jira has no milestone; the convention here is the label `milestone` (or an issue type of that name), and it only changes how a date is drawn.

**Undo covers dragging a bar and the % handle, this session only** (`undo.ts`; button and Ctrl/Cmd+Z, never while typing or with a dialog open). It writes the old values back through the same PATCH and works out the next step from what the previous one left behind — restoring the dragged task makes the cascade pull its zero-slack successors back by itself, and those then need no write. Modal edits, bulk edits, status and assignee changes are deliberately not undoable: they are Jira writes with side effects (a transition can notify people).

**Import reads CSV and Excel pasted cells, not .xlsx** (`csvImport.ts`, `ImportModal`, `TaskService.importTasks`; reading a real .xlsx would add a spreadsheet library). Columns are matched by header (Vietnamese or English), dates are day-first, Excel day-numbers work, and a parent is an existing key or `#N` — a row of the same sheet — so one sheet can carry a whole WBS. A row whose cell cannot be read is *named* and blocked, and so are its children; nothing is guessed. A long sheet is sent in pieces of 25 because one request must stay inside Cloud Run's 300 s, and `prepareChunk` rewrites each `#N` for the piece it lands in (an earlier piece's row → the key it became, a row in this piece → its place in this piece). The server cap is 200 rows and it returns `rowKeys` for exactly that.

### Timesheet

`server/src/timesheet.ts` reads and writes **Jira worklogs only** — no table of ours, for the same reason the board has none: a second copy of logged time would disagree with Jira's own reports. A range is fetched by JQL `worklogDate` widened a day each side (it's evaluated in the Jira profile's timezone, not the browser's), then cut exactly on each worklog's `started` instant in the browser's `tzOffsetMinutes`; issues with more than the 20 worklogs a search hit embeds are re-read per issue. Every project member gets a row even with nothing logged — "who hasn't logged" is half the point — plus anyone who logged without being a member (flagged). Capacity and leave come from `resource_profile`/`resource_absence`, defaulting to 8h. "Expected" counts working days up to today; "chưa ghi" marks only days *before* today.

**Time is always logged as the signed-in user** — Jira records the token's owner as author and offers no "log for someone else" to a 3LO app, so the UI and the chat's `log_work` say so rather than pretending. `started` must be `yyyy-MM-ddTHH:mm:ss.SSS+0700` (offset without a colon) or Jira 400s; work is stamped 09:00 local so it stays on the chosen day in every view. `adjustEstimate=leave` keeps the Original estimate a plan rather than a countdown. The chat has `log_work`, `timesheet` (who logged what, who has gaps) and `update_task.estimateHours`.

### Board, reports and resources, stage 3 (phase 2 · stage 3)

**Board.** The board's own *quick filters* are read (`getBoardQuickFilters`, read scope) and shown as chips; switching one on asks `GET /board/quickfilters/keys` (ids ANDed, run by Jira over the board, ids checked against this board's list, keys cut to the project) and `matchesFilter(issue, f, today, quickKeys)` keeps only those keys. `quickKeys` is `null` until Jira answers or if it refuses — then it restricts nothing, so a bad quick filter never blanks the board. *Card layout and colours* (`cardOptions.ts`, per board in localStorage) are pure and tested; a blocked card keeps its red edge over any colour scheme. A flag is written through the site's "Flagged" checkbox field (`fieldDiscovery.getFlaggedFieldId`) because the agile API only *reads* `flagged`. Sub-tasks are grouped from the **whole** snapshot (`subtasksByParent`), so a parent lists its own even when a filter hides them. **Deleting a sprint needs its own scope** (`delete:sprint:jira-software`) behind `JIRA_AGILE_DELETE`, for the same reason `JIRA_AGILE` exists: a scope the Atlassian app lacks fails `/authorize` for everyone. The backlog's Epic/Version panel counts the whole board (not the filtered list) so the next Epic can still be picked; bulk edits and per-row status changes go one issue at a time through `updateTask` (so the Epic rule, transition fields and the cascade still apply). The backlog selection bar still appears only at ≥2 rows — at 1 it would shift the table between the two clicks of a double-click (same bug as the WBS).

**Capacity.** `availability()` now returns `capacityHours`; `GET /board/sprints/:id/capacity` (not staff-only) and the AI plan both feed `CapacityTable`, and `capacityRows` subtracts assigned hours only when the board estimates in **hours** — points do not convert to hours, so no "remaining" is invented.

**Reports.** `sprintReport.ts` rebuilds committed / added / completed and the burnup from each issue's Sprint-field changelog (Jira's own sprint report has no public API); weights are *current* estimates and an issue removed and never returned is no longer found by `sprint = X`. `flowMetrics.ts` (pure) + `flowReports.ts` give cumulative flow, cycle/lead time and created-vs-resolved from **one** `expand=changelog` search (≤90 days, ≤1000 issues, 10-minute memory cache per site+account+project+window; Jira returns at most the newest 100 changes per issue). `progress_snapshot` (migration 011) keeps one measured row per project per day, written by whoever opens the report page (unscoped view, date within ~a day of server today, refreshed at most every 3 hours) — there is no background process to do it. A report link is `/?project=KEY&report=<uuid>` (`deepLink.ts`): parked in sessionStorage so it survives the OAuth round trip, then `App` switches the tab to that project and opens the Báo cáo tab; it grants nothing (`requireProject` still decides).

**Resources.** Skills are `resource_profile.skills` (the AI planner already reads them); `skillMatrix.ts` folds case/diacritics so "React"/"react" are one column. Leave periods can be edited (`PATCH /resources/absences/:id`, range checked in the store). The heatmap gained month columns and `shiftWindow` (a window of whole months moves by months). Worklogs can be edited by their author only; `date` is sent only when it changed so a same-day edit keeps the original time of day.

### KBKT import (test-case workbooks → Jira)

`server/src/kbkt/` is `jira_sync.py` (the testers' script: one KBKT workbook → a Story, a Sub Testcase per test row, a Sub Bug per bug, screenshots, test↔bug links) moved onto the site, run with the user's own OAuth token. The entry is **"Nhập KBKT" in the Gantt toolbar's "Nhập / Xuất" menu, beside "Xuất CSV"**, not in the header: one more button there wrapped it to two rows at 1500px, and the wrapped layout made the whole page unclickable in e2e. `parse.ts` reads the workbook, `specs.ts` (pure) builds the desired issues, `sync.ts` compares with Jira and writes; `routes/kbkt.ts` has `preview` (dry run, JSON) and `apply` (SSE, same headers as the chat). Nothing is stored between the two — apply re-parses the upload and re-reads Jira, exactly like the script without and then with `--apply`. Not staff-only: nothing bills a shared key, and Jira's permissions on the user's token are the gate.

- **Labels are the compatibility contract.** Issues are found by `kbkt-<code>`, `story-`, `tc-<code>_<n>`, `bug-<code>_<BUG-nn>`, `result-*` — byte-identical to the script's (whitespace → `_`), so issues it already created are updated, not duplicated, and re-applying a file changes nothing. Never route them through taskService's `cleanLabels` (it folds to `-`). Screenshot filenames (`<code>_<BUG>_<i>.<ext>`) are matched the same way. `specs.ts` was diffed against the Python `build_specs` on five real workbooks (615 specs, identical); keep it that way when changing either.
- **Not exceljs.** openpyxl writes drawing XML in the default namespace (`<wsDr>`, not `xdr:wsDr`), absolute relationship targets, and every non-ASCII character as `&#nnnn;`; exceljs crashed on every workbook with a screenshot. `kbkt/xlsx.ts` is a small reader on `fflate` + `fast-xml-parser` with namespace prefixes stripped and its own single-pass entity decoder. A formula without a cached value and a merged cell's non-anchor cells read as empty — what openpyxl reports, and what the script's rules assume.
- **Scoped to the session's project.** The script followed an existing Story into any project; here a Story key from another project is an error naming the project to switch to. `storyKey` is tri-state: absent = the key in the file name (missing in Jira → new Story, the script's behaviour), `"new"` = the file's own Story (created once, then found again by its `story-<code>` label — not a new one per import), a key = that issue, which must exist.
- **Each file picks its target in the dialog: "Story có sẵn" or "Story riêng của file".** The existing-Story picker searches `GET /kbkt/stories?q=` (a key or "33", or title words; Story level only, 30 results, never the whole project). A file named `AI-33_…` pre-selects AI-33 after confirming it exists, and falls back to its own Story with a note if not. **The Epic is sent only with "Story riêng"**: given an Epic, the sync moves an existing Story into it (the script's `--parent`), which is not what "put these test cases under AI-33" means. Sub-issues already synced under another Story are re-parented to the chosen one (an UPDATE of `parent`).
- **Batched for Cloud Run's 300s.** New sub-issues go through `POST /issue/bulk` (50 per call; `bulkCreateIssues` maps per-element errors back by index, including the all-failed 400); each issue type's starting status is read once after creating; transitions are cached per (issue type, status); the remaining calls run four at a time. A 401 ends the run, any other Jira error is logged and the run continues; closing the stream stops it between calls, and re-applying carries on by label.
- **Settings per project** in `kbkt_import_settings` (migration 009): one jsonb blob — issue type names, status per test result / bug state, severity → priority, link type, which kinds get the due date. Defaults are the script's `jira_sync_config.json`; names are resolved against the project on every run (folded, so "Sub Bug" matches "Sub-Bug") and a mismatch is an error listing what the project has.
- **Parts of a test case / bug go into the project's own fields** (`kbkt/fields.ts`). Each description section has a stable key (`section`, `steps`, `expected`, `actual`… on `Spec.sections`); on every run the sync reads the Sub Testcase / Sub Bug **create screen** (`getCreateMetaFields`, createmeta) and routes a section to a field — the saved `fieldMap` for that kind, or, when none is saved, by field *name* (`FIELD_SOURCES[].defaults`: Module ← Nhóm, Test Steps ← Các bước thực hiện, Expected/Actual Result, Severity, Root Cause, Steps to Reproduce…). A routed section leaves the description; the rest stays exactly as the script wrote it, so a project without such fields sees no change and `buildSpecs`' own `description` still equals the script's. Field ids are per site, so none is hard-coded. Writable kinds only: textarea → ADF, one-line text → string ≤255, single select → an option matched with folding (no match: the value stays in the description, warned once); users/dates/multi-selects are not offered. A field the screen lacks is a warning and its section stays in the description, never a failed create; an unreadable screen leaves everything in the description. An empty cell **clears** its field on update (the file is the source of truth). Issues created before this get their content moved on the next import (an UPDATE naming the fields), then compare equal. The workbook has no Pre-conditions or Test Data column, so those fields stay empty.
- No `task_overlay` rows are written (the script wrote none). Sub-issues carry only a due date, so they are not Gantt bars.

Tests: `server/test/kbkt*.test.ts` build workbooks in memory the way openpyxl writes them (`kbktFixture.ts`) and sync against `kbktFakeJira.ts`; the e2e stand-in runs the real parser and engine on that fake (`e2e/kbkt-import.e2e.mjs`). Writes to real Jira: checklist section C.

### Progress report

The Báo cáo tab applies the planner's rule to reporting: **`server/src/progress.ts` computes every figure, the model only explains them.** Asked "how far along are we?", a model produces a confident percentage with nothing behind it. `computeProgress(tasks, asOf)` is pure and is the one source for the report page, the AI narrative and the chat assistant (`project_progress` tool, plus a one-line `progressHeadline` in every chat system prompt), so a number on the page and a number in the chat cannot disagree.

How the numbers are defined — each choice fixes a way the obvious version lies:
- **Work items are leaf, assignable tasks.** A Story with sub-tasks is excluded (its sub-tasks are counted — both would double-count the same effort) and every Epic is excluded (a container, see `isAssignableType`).
- **% is duration-weighted over *scheduled* work only**, done = 100% regardless of the overlay value. Actual and planned share one denominator: undated tasks have no plan to be ahead of or behind, and counting them on one side only would bias SPI. They are reported as a count instead.
- **Planned % is measured against the baseline, falling back to current dates only when there is none** — measuring against current (already-slipped) dates would make a late project look on plan because its plan moved. `counts.noBaseline` is surfaced on the page for exactly that reason: work with no baseline can never look behind.
- **SPI is null until the plan expects ≥10%** — at 1% planned / 0% done it is pure noise.
- **Health is decided by `judgeHealth`'s explicit rules** (SPI bands, slip vs baseline, critical-path overdue, overdue share, not-started), each contributing a Vietnamese reason; the worst verdict wins. The model receives the verdict and reasons as facts and is told not to contradict them.
- **"Critical" uses `server/src/criticalPath.ts`, a straight mirror of `client/src/criticalPath.ts`**, so a task flagged critical in the report is the same one painted red on the Gantt. Change one, change both.

**The AI is for reasoning, not restating.** The page draws every figure as a chart (`client/src/components/progressCharts.tsx`), so a narrative that repeats "35% vs 59%" in prose adds nothing. `server/src/ai/reportContext.ts` hands the model the task *graph* instead — open work ranked by urgency with `blockedBy` (unfinished predecessors), `openDependants`, owner, dates and a description excerpt for the most urgent items, plus each person's peak concurrent tasks over the next 14 days and the full team list — and the schema asks for what only inference can give: `insights` (bottleneck / dependency / people / scope / data / momentum), an `outlook` forecast with a confidence, risks with a `mitigation`, and recommendations with `priority` and an `owner`. Two lines stay hard: the model may quote figures but never produce new ones, and `outlook` **may disagree** with the measured `health` (numbers on track, but the next critical task has no owner — exactly the judgement we want) while never overwriting it; the page labels it "Dự báo của AI" and flags the disagreement. `normalize()` drops unknown issue keys and any owner not on the team. All the new narrative fields are optional in the client type, because reports saved before them must still open.

The page is **two panes**: the computed dashboard on the left and `AiBrief` on the right, on its own dark-headed surface with its own scroll, so a forecast is never mistaken for a measured number (below 1180px they stack, AI first). Every chart is a way in — a donut segment, a phase or person bar, an attention tile, a data-quality chip or an AI item's issue keys opens `TaskDrawer`, which resolves the list from the workspace's live `tasks` with progress.ts's definitions (leaf, assignable work) rather than the metric lists, which are capped at 25.

Live numbers and the AI narrative are **two layers with two lifetimes**. `GET /api/progress` recomputes from Jira on every visit (free, never stale). `POST /api/progress/reports` costs a Gemini call, so it runs only on request and stores the narrative *together with the metrics snapshot it was written from* in `ai_progress_report` — a report from last Monday must keep saying what it said on Monday. The page shows when the narrative was written and warns when the live numbers have moved since. `actual_pct`/`planned_pct`/`health` are columns (not only JSON) so the trend chart is one indexed query. `ai/report.ts`'s `normalize()` drops any issue key the model cites that isn't in the project, and `ai/progressReport.ts` is the single compute→narrate→store path used by both the page button and the chat's `create_progress_report` tool.

"Today" comes from the **browser's local date** for both the page (`?asOf=`) and the chat (`today` in the POST body): server UTC is a day behind in Vietnam until 07:00, which would move tasks in and out of "overdue" depending on the hour.

**The live dashboard can be scoped; the AI report cannot.** `GET /api/progress` takes `assignee`, `epic` and `type` (plus `asOf`) and passes them to `computeProgress(tasks, asOf, scope)`. The scope narrows the work items **after** the leaf test and the critical path is still computed over the whole graph: filtering first would turn a Story whose sub-tasks belong to someone else into a leaf of its own and count it as work for the wrong person. `resolveDrill` in `ProgressReportView.tsx` applies the same narrowing so a drawer lists exactly what the chart counted — change one, change both. A saved report is written over the whole project as of its own day, so while the dashboard is scoped or on another date `AiBrief` gets `live={null}` and shows no "numbers moved" warning. Saved reports are deleted **softly** (`deleted_at`, migration 006, staff only): their token counters are part of the AI spend ledger, same as chat sessions.

### AI planner

`server/src/ai/` turns a plain-language brief into a work breakdown. One Gemini call (`@google/genai`, `GEMINI_API_KEY`, shared with the video-agent service), then everything numeric is computed here rather than asked for.

The split is the design: **the model decides semantics, this code decides every number.** It returns tasks, durations in days, FS/SS/FF/SF edges and an assignee; `planner.layoutSchedule()` derives the actual dates from those durations and the graph, using the same earliest-start rules as `applyDependencyCascade`, so the preview a reviewer approves is what the live cascade will enforce. Asking a model for dates gets you a schedule that contradicts its own dependency list.

`responseSchema` (constrained decoding) guarantees the *shape*, never the meaning, so `normalize()` re-checks everything that only fails later: an issue type this project doesn't have (validated against `listIssueTypes()`, not the hard-coded `IssueTypeName` union), an assignee who isn't on the team, an edge pointing at a `tempId` the model never emitted, and cycles — each corrected and surfaced to the reviewer as a warning rather than silently accepted or thrown away.

**Nothing reaches Jira without a human.** Generation writes to `ai_plan_run`/`ai_plan_item` only; `POST /api/ai/plans/:id/apply` is the sole route that creates issues, in two passes — parents before children (Jira rejects an unborn parent key), then dependencies once every `tempId` resolves to a real issue key. Partial failure is reported per row, not rolled back: issues already created in Jira cannot be unmade, so the run stays `proposed` and the applied rows carry `applied_issue_key`. **Every plan route starts from `planStore.getRun(cloudId, projectKey, runId)`**, which scopes by site *and* project and treats a malformed id as not-found: edit, delete-item and discard once trusted the URL's ids after (or without) a cloud-only lookup, so another project's run could be discarded or have its items changed.

The model is `GEMINI_MODEL` (default in `planner.ts`), and it must be set as a **repo variable** in the deploy workflow — `env_vars_update_strategy: overwrite` means a value set on the Cloud Run service by hand is wiped on the next deploy. `GET /api/ai/models` lists what the key can actually call, filtered to `generateContent`: model names are added and retired continuously, so a list written into source or docs is wrong within weeks, and a stale `GEMINI_MODEL` surfaces as a 404 on the next plan rather than at deploy time.

Not built yet: PRD/BRD upload with RAG. `pgvector` is why Postgres was chosen and why docker-compose uses the `pgvector/pgvector` image, but no vector tables exist.

### Gantt rendering reaches into gantt-task-react's own DOM

`gantt-task-react` (pinned `^0.3.9`) exposes no prop for two things this app needed, so `GanttView.tsx` reaches into its rendered SVG directly instead — the same technique `DependencyOverlay.tsx` already used for drawing FS/SS/FF/SF arrows:

- **Day-view labels.** The library always renders "Th 2, 15" (weekday + day) with no way to ask for just the day number, and at a fixed pixel width regardless of zoom. A `MutationObserver` finds every calendar-header `<text>` — queried across `bodyEl`'s whole subtree, **not** scoped to "the first `<svg>`" first: gantt-task-react renders the calendar header and the bar grid as two separate sibling `<svg>` elements (`TaskGantt`'s JSX), and grabbing the wrong one silently finds nothing (this was a real bug: the label never shrank because `querySelector("svg")` wasn't reliably the header one). Matched by the compiled CSS module class (`_9w8d5` — coupled to the exact installed version; if a bump changes it, the effect just no-ops and the old format reappears, not a crash), trimmed to its trailing day number, and blanked on every Nth label once `columnWidth` is too narrow for all of them to fit without overlapping.
- **Bar label contrast.** The library hard-codes white fill (`._3zRJQ`) for text drawn inside a bar. Every bar background here is a light pastel (see below), so white-on-pastel is low-contrast — overridden globally in `App.css` with `!important`, since there's no per-task hook to win the cascade otherwise.

**A big list is drawn a window at a time** (`client/src/ganttWindow.ts`, `VirtualStage` and `WbsListTable` in `GanttView.tsx`). gantt-task-react draws every row it is given, so thousands of tasks meant tens of thousands of DOM nodes and every scroll, click and drag paid for all of them. Past `WINDOW_THRESHOLD` (250) rows the library gets only ~120 rows around the viewport; below it nothing changes (small projects keep the old, whole-chart path, which is what the other e2e files exercise). How it holds together, because each piece is load-bearing:
- **The page's native scrollbar drives it**: a `.gantt-vscroll` scroller holds a spacer as tall as the whole list and a sticky `.gantt-stage` with the chart in it. `VirtualStage` swallows plain vertical wheel events in the capture phase (the library would otherwise scroll its own container and `preventDefault`); sideways, Shift and Ctrl+wheel still reach the chart. The library's own vertical scrollbar is hidden by its compiled class `_1eT-t` (like `_9w8d5`); if an upgrade renames it the cost is two scrollbars.
- **Rows move by a CSS variable, not by state**: `--gms-row-offset` on the stage = `scrollTop − firstDrawnRow × ROW_HEIGHT`, applied by `.wbs-rows` and the bars' SVG as a `translateY`. A scroll event only writes the variable; the window itself moves in steps of `CHUNK_ROWS` (20) with `BUFFER_ROWS` (40) either side.
- **The table follows the library, not GanttView**: the library adopts a new window one render after it is asked, so `WbsListTable` builds its rows from the `tasks` prop the library hands it, and reports `onCommitted(firstRow, count)` from a layout effect — the same commit that put the rows and bars in the DOM. That is what keeps a row and its bar on one line, and what updates the offset in the same frame. The overlays (`rowTasks`, `measureKey`) follow the `drawn` state set by that callback, never the requested window: they read bars by index from the DOM, and the observer only watches attributes, so it would not notice new bars arriving.
- **Two invisible tasks pin the date axis** (`axisSentinels`): the library sizes the axis from the tasks it is given, and a sliding window would otherwise slide the whole chart sideways. They sit after the real rows and are never drawn into view.
- Things that need every row (`rows`: shift-range selection, `goToToday`, the CSV export) still use the full list. `e2e/gantt-scroll.e2e.mjs` checks row/bar alignment at the top, middle and end, the last row reachable, dblclick/drag/select on the right task, the axis not shifting, sideways scrolling steady and frame times; `e2e/perf-scroll.mjs [rows]` measures.

**Scrolling is kept cheap by a build-time patch of the library** (`client/vite.gantt-patch.ts`, registered in `vite.config.ts`; dev needs `optimizeDeps.exclude` for it to apply). gantt-task-react keeps scroll position in React state and re-renders its whole tree on every wheel event, and its effect that rebuilds every bar and the date range lists `scrollX` as a dependency (only right-to-left needs it) — so each step of a horizontal scroll re-ran O(rows) work and handed the children a fresh `tasks` array. The patch changes that dependency to `rtl ? scrollX : 0` and wraps `Calendar`, `Grid` and `TaskGanttContent` in `React.memo` (the last ignores `setSelectedTask`, a closure rebuilt every render that only reads props the comparator already checks). It is a text patch that **fails the build** if a library upgrade moves the code it expects; `e2e/gantt-scroll.e2e.mjs` fails on 100 ms+ frames on a 1500-row chart and `e2e/perf-scroll.mjs [rows]` is the measuring tool (frame times plus a CPU profile; `INCLUSIVE=1` on a dev build names components). The WBS header and table are `useMemo`'d elements handed through `WbsListContext` for the same reason — the library re-renders the list component on every scroll, and rebuilding N rows each time was the other half of it. The overlays' `measure()` (`useBarRects`, `BaselineOverlay`) must stay idempotent (keep the previous state when nothing moved) and runs once per frame: an unconditional `setState` there re-rendered every arrow on any attribute change in the chart.

**Zoom is one continuous variable, `pixelsPerDay`, not per-mode column widths.** `pickScale()` in `GanttView.tsx` derives *both* which of Day/Week/Month is showing *and* that mode's `columnWidth` from it — there is no separate viewMode state to fall out of sync with the width. A column's width is always `pixelsPerDay * daysPerColumn(mode)` (Day=1, Week=7, Month≈30.4, from the library's own `seedDates`), so the same zoom gesture shrinks every mode's columns at the same rate, and whichever mode's resulting width first lands inside `[MIN_COLUMN_WIDTH, MAX_COLUMN_WIDTH]` — preferring the finest granularity that still fits — is the one rendered. That's the auto Day→Week→Month handoff as you zoom out (and back as you zoom in), with no separate threshold logic outside this one function. The Day/Week/Month buttons just jump `pixelsPerDay` to that mode's old fixed default (`DEFAULT_PIXELS_PER_DAY`), landing exactly where the buttons always used to.

A native (non-passive) `wheel` listener on `.gantt-body` — not React's `onWheel`, which React attaches passively by default, where `preventDefault()` is silently ignored — checks `e.ctrlKey` (how browsers report trackpad pinch, specifically so a page can override the browser's own page-zoom) and adjusts `pixelsPerDay`. Row height is untouched, so vertical scale never moves.

**An Epic's bar is always its children's min/max span**, even when the Epic issue itself carries its own Jira dates — `resolveRanges()` in `ganttMapping.ts` checks Epic-with-children before checking the task's own `startDate`, the opposite priority from every other WBS parent (a Story with sub-tasks keeps its own dates as authoritative, per the BUG already documented there). Dragging is disabled (`isDisabled` in `toGanttTasks()`) for an Epic that has children, since its bar would just snap back to the rollup on the next render otherwise; a childless Epic stays draggable.

**Baseline strips** (`BaselineOverlay.tsx`, toggled by the "Baseline" switch in the toolbar's "Hiển thị" panel, remembered in `gms.gantt.baseline`) use DependencyOverlay's technique — portal into the bars SVG, read each bar's `<rect>` by row index — and draw in the ~8px gap the library leaves under every bar, so they never cover a bar or its handles. Position is anchored on the actual bar, not on a date→x formula of our own (`baselineGeometry.baselineBox`): the bar's left edge is its start date, and the scale is read off the bar itself, which stays exact in Month view's uneven months; only a bar drawn at the library's 16px minimum falls back to the zoom's nominal px/day. An Epic with children is compared against its children's baseline span (`resolveBaselines`), mirroring its bar. Its MutationObserver also sees its own strips land, so `measure()` keeps the previous state when nothing moved — without that it is a render loop.

**Bar colours are a hash of the task id into a fixed hue palette** (`PALETTE_HUES` in `ganttMapping.ts`) — "random" meaning varied per task and stable across renders, not re-rolled each time. Saturation and lightness are fixed and only hue varies, which is the actual mechanism for "random but harmonious": any two neighbours still read as one matched set. Bug keeps its old fixed red (worth being able to spot at a glance across a hundred bars) and Epic gets a bolder, more saturated version of its own hash-hue rather than a fully separate colour.

### Client structure

`App.tsx` is a ~50-line auth shell: `useSession()` runs before any branch (keeping `react/rules-of-hooks` satisfied), then it renders `LoginScreen`, `ProjectPicker` or `ProjectWorkspace`. There is no router — the OAuth callback is a *server* route, so the browser never sees `?code=`, only an optional `?auth_error=`.

**Opening a project shows the last copy first** (`client/src/tasksCache.ts`): `ProjectWorkspace` starts from what this browser saved (tasks + users, `localStorage`, keyed by site **and account** and project — what someone may see depends on their Jira permissions, so another account on the same computer must never be handed it; logout clears every entry) and swaps the fresh copy in when `loadAll` returns, with the toolbar button reading "Đang cập nhật…". A response that was requested before the user's first drag/edit is not applied (`seqCounter` moved), since it would put the old schedule back; a failed refresh keeps the cached data on screen with a notice instead of an error page. `GET /api/tasks` leaves **descriptions out** (`listTasks({ description: false })`, the heaviest field): `Task.description` is `undefined` = not fetched vs `null` = empty, and `TaskEditModal` fetches it from `GET /tasks/:id/description` on open. Until it arrives the box is locked and the save **omits** `description` — sending the empty string would wipe what Jira holds. Server-side callers that want it (assistant, digests, reports) keep the default, `listTasks()`. **The Bảng, Chấm công and Báo cáo tabs reopen on their last answer** (`client/src/viewCache.ts`: memory, written through to `sessionStorage` so an F5 paints from it too — only the Gantt used to survive a reload — keyed by site + account + project, cleared on logout; it also holds the resource pool, see below): each tab is unmounted when you leave it, so without this every visit started blank and waited on Jira. The fresh answer still replaces it; Bảng and Báo cáo take `refreshing` (the workspace is still on its saved tasks) and wait for it, because `tasks` changes twice on that path and each change would otherwise cost the server a full read. `GET /api/progress` lists tasks **without descriptions** — `computeProgress` never reads them, and they are the heaviest field. Board and timesheet reads log a `[perf]` line like `listTasks` does. `listTasks` logs one `[perf]` line per call (Jira, Postgres, reconcile, persist, total) so a slow load can be attributed from the Cloud Run logs instead of guessed; the service keeps `--min-instances=0`, so the first request after idle also pays for a cold start.

**A project belongs to a tab, not to the browser** (`server/src/auth/projectScope.ts`, `api.ts` `setTabProject`). The session cookie holds one `projectKey` and every tab of a browser shares it, so opening project B in a second tab used to rewrite it and tab A's next request ran against B — two projects could not be worked on side by side. Each tab now keeps its own project in `sessionStorage` (`gms.tab.project`, set from `/auth/me` and from the picker) and sends it as `X-Project-Key` on every call (`projectHeaders()`: `request`, the chat stream, the KBKT upload). `requireProject` takes the project from the header — checked against the projects the account can browse (`pickProject`, cached 5 minutes, one re-list when a key is missing from an older list) and refused with 403 `PROJECT_NOT_ACCESSIBLE` if not, never swapped for the cookie's — and rewrites `auth.session.projectKey/projectName` for that request, so every route that reads `session.projectKey` is per-tab for free. `/auth/me` resolves the same way. The cookie's project is now only the **default**: a tab with nothing pinned (a new tab, a fresh login, the stand-in API) takes the last project chosen anywhere. Anything new that calls `fetch` against `/api` directly must add `projectHeaders()`. Per-project client state (`tasksCache`, `viewCache`, chat session id) was already keyed by project, so tabs do not share it by mistake; preferences not keyed by project (columns, divider) are shared on purpose. `e2e/multi-tab.e2e.mjs` drives two pages of one context.

`ProjectWorkspace` holds all the project state and is keyed on the project key, so switching project remounts the subtree and discards tasks/users/collapse/selection rather than resetting seven fields by hand. After any mutation it calls `refreshTasks()` on top of the optimistic single-task update, because a cascade can move *other* tasks server-side.

`api.ts` sends `credentials: "include"` on every call and routes 401s through a module-level handler so any failed call pulls the app back to the login screen. A 403 must **not** log out: Jira returns 401 for a dead token and 403 for a permission problem, and `server/src/errors.ts` preserves that distinction across the whole API.

Selection is file-manager style: click selects one, Ctrl/Cmd toggles, Shift extends a range measured in the **visible row order** (post-filter, post-collapse) — see `GanttView`'s `onSelect`. A global `keydown` in `ProjectWorkspace` handles Escape: closes the edit modal if one is open, otherwise clears the selection, never both at once.

**Header and toolbar are progressive** (a ~35-button wall was cut to two layers). `Toolbar.tsx` is the header, 36px controls: the project badge is the project switcher (a menu whose one action opens `ProjectPicker` — it lists no projects itself), underline tabs (`aria-current`), "Đồng bộ từ Jira" as a ghost button, "Task mới" as the only solid one, and the avatar menu holding the name and "Đăng xuất". The Gantt's toolbar is `FilterBar` in one 48px row of 32px controls. Left: search with the JQL switch inside it, saved filters, "Của tôi", "Quá hạn", "Chưa có ngày (n)", then a single "Bộ lọc" panel with one collapsible section per value facet. Right (`trailing`): the Ngày/Tuần/Tháng segmented control, "Hôm nay", undo/collapse/expand as icon buttons, a "Hiển thị" panel (Đường găng/Phụ thuộc/Baseline switches plus the WBS columns), a "Nhập / Xuất" menu and a `?` panel with the selection shortcuts. Active facets are removable chips on a second line that exists only while something filters (`.tf-active`, with the count and "Xoá lọc"); the JQL panel never adds a row, and an applied JQL shows as a chip that reopens it. The resource tab uses the same `FilterBar`, just with fewer facets. `Popover.tsx` is the shared trigger+panel: outside click, Tab-away and Escape close it, and `role="menu"` panels take arrow keys. Escape is handled on the React tree and stops there on purpose — the workspace listens for Escape on `window` to clear the Gantt selection, and closing a menu must not also do that. The row drops its right group onto a second line when the left one can no longer shrink, and below 1400px "Hiển thị" and "Nhập / Xuất" keep only their icon (they carry an `aria-label`). e2e drives the panels through `e2e/toolbar.mjs` (`pickFacet`, `openDisplay`, `ioAction`); `e2e/header-toolbar.e2e.mjs` checks the layout contract (one row at 1500px, 32/36px controls, one solid button, selection bar moves nothing).

**The task detail window** (`TaskEditModal.tsx`, `.modal-detail`) is two columns under a header and above a footer that stay put: the main column holds what the work *is* (title, description, attachments, schedule dependencies, issue links, comments and history — folded sections), the side panel how it is *managed*, most-used first (status, people, schedule, effort, classification). It asks before closing with unsaved changes (`dirty`), stops Escape from reaching the workspace's window-level handler, traps Tab, returns focus, and Ctrl+Enter saves. Second pass: the title is an auto-height textarea (Enter does not break it, a pasted break becomes a space); the folded sections carry counts (`Đính kèm`, `Phụ thuộc lịch`, `Liên kết Jira`) and show no inner label or "Không có" box when empty; attachments are `TaskAttachmentList` rows (thumbnail for a small raster image, view / download / delete icons on hover or focus, a picture opens in `ImageLightbox` — portalled, its own Escape, so a picture never triggers the window's "Bỏ thay đổi?"); the link-URL form is folded behind "+ Thêm liên kết"; quick time-logging is folded behind "+ Ghi giờ" beside "Đã ghi"; classification is `.td-grid` rows of `label | value` (`Việc cha` goes full width under its name) and an empty components/versions list is a line of muted text, not a disabled box. The comment box is one bordered field with its send button inside it (`.td-box`), and text areas size to their text where `field-sizing` exists; Vietnamese has no browser dictionary, so the title, description and comments turn spellcheck off rather than underline every word. Tests still find fields by `.field > span` label text, `.modal-id`, `.modal-footer .primary` — keep those (`.td-row` rows are `.field`s).

**The WBS table starts with the columns a plan is scanned by** (`DEFAULT_COLUMNS`: loại, trạng thái, ưu tiên, phụ trách, %), the divider sits at what those columns and a readable name need rather than at half the window, and where it is dragged to is remembered (`gms.gantt.listWidth`, dropped when the column set changes). Row text is `user-select: none`: Shift+click selects a range, and the browser's own text selection painted the cells blue on top of it.

**One design layer, three token layers** (`client/src/design/`; the `design-system` skill's structure). **Before any UI change read `design-system/gms-prjmanagement/MASTER.md`, then `pages/<page>.md` if one exists (it overrides Master)** — they hold the rules and the pre-delivery checklist; the values themselves live in `tokens.css`, so when the two disagree fix the markdown to match the code. `tokens.css` is the only place a raw colour, radius, shadow or size is defined: *primitive* (a blue, a spacing step) → *semantic* (primary, border, surface, danger) → *component* (`--control-*` for a field, `--menu-*` for a panel and the list a select opens, `--dialog-*`). App.css and components reference the last two layers; add or change a token rather than writing a hex. `controls.css` is what a bare `<input>`, `<select>`, `<textarea>` looks like anywhere, written in `:where()` so it has no specificity and any component that styles its own field simply wins; a new field needs no class to match the rest. Selects use `appearance: base-select` (Chrome 135+) so the list that opens is ours — same panel, rows, selected tick as every menu — and fall back to the platform's list with our closed state and chevron elsewhere; do not give a `<select>` its own `appearance` or chevron. Toolbar fields are 32px through the "Compact form controls" block at the end of App.css (add a new bare toolbar field to its selector lists). Inside a `.modal`, `.dlg` or `.field` every one-line field is one **form size** (`--control-h-form` 36px, `--control-font-size-form`, from `controls.css`) — a text box, date, number and select no longer differ by a few pixels, and a button in a row with fields (`.pred-add`, `.log-inline`, `.att-link-add`) matches; a deliberately different field (`.td-title`, the box inside `.labels-input`) sets its own `height`. Keyboard focus on a field is the `--control-ring`, not the page-wide outline, and a select's rows show the keyboard position by fill only. **No `<datalist>`**: the browser draws its list itself; `SuggestInput` (portalled, same `--menu-*` panel, arrow keys/Enter/Esc) is the completion box for labels and issue keys. The native date picker is the one popup still not ours.

**Browser dialogs are not used** (`components/Dialog.tsx`, hook in `dialogContext.ts`, mounted in `main.tsx`): `window.confirm/prompt` drew the browser's own window, unstyleable and with the page address in it. `useDialogs()` gives `confirm({ message, tone: "danger" })` and `prompt({ title, initial })`, both promises; Esc/outside click cancel, Enter confirms, Tab stays inside, focus returns. A destructive confirm focuses Cancel. e2e answers them through `.dlg` (`button.danger-solid` / `button.primary`), and `transition-fields.e2e.mjs` asserts no native dialog opens.

**Two things keep a double-click on a WBS row working, and each alone is not enough.** (1) `GanttView` hands `gantt-task-react` `WbsListHeader`/`WbsListTable`, module-level components with a fixed identity that pull the current render closures from `WbsListContext`. Defined inline in render they were a new component *type* every time, so the first click (select → re-render) rebuilt the row under the pointer and no `dblclick` fired. (2) Nothing may take layout space on selection: the bulk-action bar (`.selection-bar`) is `position: fixed` at the bottom of the window, out of the flow, and there is no idle hint strip (the help is the toolbar's `?` panel). A strip above the table that appeared only on selection pushed the table down ~45px between the two clicks and the second landed on another row. The bar floats at the bottom rather than over the toolbar because one click selects, so it is on screen most of the time and would hide search and zoom. Don't make either conditional or inline again; `e2e/wbs-dblclick.e2e.mjs` checks both.

`server/src/adf.ts`'s `textToAdf()` wraps a bare `http(s)` URL in ADF's `link` mark rather than leaving it as plain text — a link pasted in from an import file (an image URL, a shared doc) needs to land in Jira as something clickable. The link lives on the issue's `description` field only, never in the overlay/database.

WBS hierarchy is ours, not the Gantt library's: `ganttMapping.orderByWbs()` does the depth-first ordering and `toGanttTasks()` emits every row as `type: "task"` — `gantt-task-react`'s own project/child aggregation is bypassed, and the tree is rendered by the custom `TaskListHeader`/`TaskListTable` components inside `GanttView`. Tasks without a `startDate` are dropped from the chart.

## Known constraints

- `IssueTypeName` is still a hard-coded union (`Epic|Story|Task|Bug|Sub-task`) on the wire. The create form and the board's quick-create now offer the project's real types (`/issue-types`) and cast, so renamed types work there, but anything still typed against the union — and `createTask`'s default — assumes the stock names.
- Cross-project predecessors are rejected with a 400. The cascade only loads issues from the session's project, so a foreign key would appear to exist while never being enforced.
- An overlay-only PATCH (%, predecessors, baselines) touches no Jira field. `updateTask` does a `getIssue` visibility check in that case so a user who cannot see the issue cannot rewrite shared schedule data, but there is no write-level permission check.
- A cascade is several statements, not one transaction, so two concurrent cascades over the same tasks can still interleave — but each individual write is now atomic, which is what `--max-instances=1` used to be standing in for.
- Logout is local only — Atlassian publishes no endpoint to revoke a 3LO refresh token. Don't imply otherwise in UI copy.
